# AI 協作紀錄

工具：Claude Code（VS Code 擴充套件）。只記重要的協作與決策。

## 規劃

- **README 與 .gitignore**：由 AI 撰寫；`.gitignore` 由 AI 主動補上 `.env`、venv、SQLite 檔。我決定排除 CLAUDE.md，因為它和 README 內容重疊，做報告時再說明。
- **對照作業要求**：我把作業 PDF 交給 AI 對照計畫。AI 指出 MCP 是 +10% 加分，原計畫卻排在最先砍，成本又低。我決定把 MCP 提前到 P1 完成後就做。
- **MCP 範圍**：AI 建議只做 2～4 個工具。我決定除了 `explain_word` 以外，所有能做成工具的功能都做；工具跟著功能走，功能被砍就不做。

## 斷詞（tokenizer）

- **環境與斷詞驗證**：AI 建立 venv、安裝 SudachiPy，先用典型句子（被動、使役、複合動詞、英數混合）實測再寫程式。
- **斷詞要不要合併**：SudachiPy 把「食べました」拆成 食べ／まし／た。AI 原本的做法是自動把動詞和後面的助動詞合併成一個字，並認為讓使用者多選是加重負擔、只適合當補充功能。我認為自動合併還是可能出錯，而且 N4～N2 的使用者有能力判斷詞的界線。AI 依此實測，發現合併會把「らしい」「でしょう」「だろう」這些正是學習重點的文法吃掉，「行かなければならない」也切得不自然。我決定**不合併**，改成使用者自選範圍（Shift＋點擊選取同一句中的一段）；`tokenizer` 回傳原始切分，並同步修改規格的驗收例。
- **數字讀音**：SudachiPy 把「15」讀成「いちご」，也不處理「1本→いっぽん」這類音變。AI 比較了 num2words（只能修單純數字）和 pyopenjtalk，建議 pyopenjtalk。我問能否保證正確，AI 用 50 個常見數字＋量詞實測：SudachiPy 15/50、pyopenjtalk 49/50（錯的是 10日→とうか）。我決定採用 pyopenjtalk，並把數字和量詞合成一個 Token 作為「不合併」的例外。我原本想加使用者修正讀音的功能，後來決定不做，因為系統偶爾出錯是正常的，列為已知限制。
- **數字的 ruby**：規格原本寫「英數不加 ruby」，但「10日」合併後讀音是「とおか」，沒辦法拆給「10」和「日」。AI 提出兩個選項：整個標註，或數字都不標、只在詳情面板顯示。我決定把讀音整個標在「10日」上方。
- **Windows 路徑問題**：OpenJTalk 開不了含中文的路徑（專案在「桌面」下），AI 改成第一次使用時把字典複製到 `%LOCALAPPDATA%\furiyomi\`。

## 假名標註與文章輸入

- **API 與前端**：AI 建立 FastAPI 骨架、`/api/analyze` 與輸入頁。ruby 切分放在後端（送假名不標，如「食(た)べ」），前端只負責顯示；日文偵測以假名為準，避免中文被當成日文。
- **長文分頁**：規格原本寫超過 2,000 字就顯示提示，但我想要的是超過 2,000 字時自動切成好幾頁，用上一頁／下一頁切換。AI 建議貼上的文字和 PDF 共用同一套分頁機制，`/api/analyze` 每次仍只處理 2,000 字，在句尾切頁。我認為應該以段落為單位切，一頁才不會出現半個段落。AI 依此訂出三層規則：先在段落結尾切；段落超過 2,000 字，改在句尾切；句子超過 2,000 字，才直接切斷。AI 也提醒 PDF 抽出的文字每行都有換行，要先接回段落。我決定採用。

## 點字詳情與詞性上色（P1 完成）

- **詞性配色放後端**：AI 在 `furigana.pos_class` 把 Sudachi 詞性對應到配色分類（名詞、動詞、形容詞…），API 一起回傳，前端只套 CSS class，維持「前端只負責顯示」。
- **整段選取**：Shift 選取要判斷是否同一句，前端依後端相同的切句字元（。！？換行）計算句子編號。整段時原形、詞性沿用第一個 Token；AI 原本建議只在整段時隱藏活用形（第一個 Token 的「連用形」放在「食べました」上會誤導），我決定詳情面板完全不顯示活用形。
- **顯示／隱藏假名**：用 `visibility: hidden` 而非移除，切換時行高不變、文章不會跳動。
- **「信じ」原形錯誤**：我實際使用時發現點「信じ」原形顯示「信ずる」。AI 查出 Sudachi 把「信じ／感じ／禁じ」歸為サ変、原形給文語形；改成表記是「〜じ」時原形改回「〜じる」，原文本來寫「信ずる」就不動。
- **詞性上色開關**：我希望上色可以關掉，加了和「顯示假名」並列的開關，關閉時圖例一起隱藏。

## MCP server

- **前兩個工具**：AI 用官方 `mcp` 套件的 FastMCP 建立 `mcp_server.py`，提供 `analyze_japanese` 和 `add_furigana`。工具只呼叫 `core`，括號標音的組字邏輯放在 `furigana.bracket_text`，重用網頁 ruby 的切分，所以送假名一樣不標（食(た)べ）。`analyze_japanese` 依規格只回傳表記、原形、讀音、詞性。
- **驗證**：除了 pytest 直接呼叫工具函式，AI 也用 MCP client 經 stdio 實際連線、呼叫工具，確認 server 能正常啟動。

## AI 解釋

- **選定 OpenAI**：我有 OpenAI 的額度，所以決定用 OpenAI。AI 預設用 `gpt-4o-mini`（便宜、支援 JSON 模式），模型名稱放在 `.env`，之後可以直接換。`llm_client` 把 OpenAI 包在 Provider 介面後面，換服務只要換 Provider，測試也用假的 Provider，不連網路。
- **錯誤處理**：回傳內容缺欄位、不是 JSON 或是空字串，自動重試一次。逾時、額度不足、金鑰錯誤是服務端的問題，重試也沒用，所以 AI 建議直接回傳友善訊息、不重試。沒設定金鑰時只有 AI 解釋會顯示提示，其他功能照常運作。
- **前端**：詳情面板加上「AI 解釋」按鈕，助詞和標點不顯示。結果依「原形＋表記＋句子」暫存在記憶體，只存成功的結果。等待 AI 回應時如果點了別的字，回應回來後只存進快取，不會蓋掉目前的畫面。
- **選模型**：`gpt-4o-mini` 在「住むことにする」把「する」說成連用形、句型寫成「することにする」。AI 用同樣例子比較 `gpt-4o-mini`、`gpt-4.1-mini`、`gpt-5.4-mini`：後兩者都正確，`gpt-5.4-mini` 會寫出接續方式（Vる＋ことにする）和語感，例句時態也和原句一致。AI 建議全面用 `gpt-5.4-mini`；我決定開發測試先用 `gpt-4.1-mini`，展示時再換成 `gpt-5.4-mini`。另外確認了 Shift 選取整段（如「ことにする」）時，AI 會解釋整個句型，不會只講第一個詞。
- **調整 prompt**：用真的金鑰測試後，我發現 AI 會在說明裡重述「動詞、連用形」這些面板上已經有的資訊。我決定詞性仍然當作輸入送給 AI（幫它分辨同形詞），但說明裡不要重述；中文意思只寫譯詞，不要「意思是…」的前言。用法說明改了幾次：AI 先訂成固定項目（前後接什麼、語感、容易搞混處），我覺得太制式；改成「簡單一兩句」又太空泛。最後我決定用自然的口吻說明，有活用時提一下是什麼形，屬於固定文法句型（如「〜ことにする」）時解釋文法。

## 長文分頁與 PDF（P2 完成）

- **切頁放後端**：AI 建議切頁規則寫成 `core/paging.py` 的純函式、透過新的 `/api/paginate` 給前端用，而不是在前端 JS 另寫一份；這樣貼上文字和 PDF 走同一個函式，也維持「前端只負責顯示」。我同意。前端拿到頁面後一次只送目前這頁給 `/api/analyze`，分析過的頁面暫存，切回來不重送。
- **切段規則實作**：照之前訂的三層規則（段落 → 句尾 → 硬切）把文字拆成單位，再依序裝進頁面。句尾連同後面的「」』）」一起算，避免「…。」的 」 被切到下一頁；空行跟著上一段。測試確認所有頁面串回來等於原文。
- **PDF 接回段落**：AI 先實測 pypdf 抽出的文字，發現空行會消失，所以接回段落主要看「上一行以句尾標點結束」和「行首是全形空白（段落縮排）」；只有數字的行當作頁碼略過；每頁結尾的換行要先去掉，否則跨頁的段落會被切斷（測試抓到的）。判斷不準時由切段規則兜底。
- **PDF 錯誤處理**：不是 PDF、有密碼、沒有文字（掃描檔）、不含日文、超過 2 萬字、檔案超過 20 MB，都回傳友善訊息。
- **測試 PDF**：用 reportlab 內建的日文字型在測試中動態產生 PDF，不用把 PDF 檔放進 repo。
- **驗證**：除了 pytest，AI 也用 Playwright 開瀏覽器實際操作：貼上約 4,900 字分成 3 頁、上一頁／下一頁正常；上傳 12 頁的 PDF，行接回段落、頁碼消失，切成 3 頁。
- **MCP**：加入 `extract_pdf_text`，只呼叫 `pdf_reader` 和 `paging`。

## 單字庫（P3）

- **資料庫放哪裡**：我問要不要用電腦裡的 MongoDB 或 DB Browser for SQLite。AI 說明 SQLite 只是一個檔案，Python 內建就能讀寫，不用另外架伺服器；DB Browser 是檢視 `.db` 檔的工具，可以拿來確認資料。資料庫檔放在 `data/furiyomi.db`（不進 Git），可以用 `.env` 的 `FURIYOMI_DB` 改路徑，以防 OneDrive 同步時鎖住檔案。
- **AI 解釋快取改存 SQLite**：原本快取放在前端記憶體，重開就沒了。改存 `lookup_cache` 後，同一個字在同一句查第二次不花錢，沒設金鑰也查得到查過的字。AI 指出規格的快取鍵只有（原形, 句子），但同一句選「食べ」和「食べました」的解釋不同，所以把表記也算進雜湊。每次成功查詢都記進 `lookup_log`（命中快取也算），給統計頁用。
- **原形讀音**：AI 發現 Token 的讀音是表記的讀音（食べ → たべ），收藏「食べる」時不能直接用，所以加了 `lemma_reading`，把原形再斷詞一次取得「たべる」。
- **還沒查 AI 解釋就收藏**：AI 提出兩種做法：先存空白，或收藏時自動呼叫 AI。AI 建議先存空白，收藏才不會因為 API 出錯而失敗，我同意。後來我問「中文意思不是 AI 解釋就有了嗎」，AI 說明先收藏、後查解釋時單字庫不會更新。我決定在 AI 解釋成功時自動補上，不覆蓋已經有的中文意思。
- **一詞多義**：規格原本一個原形只存一筆，換一句收藏會提示已存在。我問不同句子怎麼辦，AI 指出「かける」（打電話／戴眼鏡）這種一詞多義會存不進去，建議維持一詞一筆、列為已知限制。我決定要支援：一個原形一筆（`vocab`），每次在新的句子收藏就多一個例句（`vocab_example`），各自保存那一句的中文意思；同一句重複收藏才提示已存在。可以刪除整個單字，也可以刪除單一例句。
- **介面用詞**：AI 把按鈕做成三種狀態（加入單字庫／加入這個例句／已在單字庫），刪除確認會列出例句數量和原句。我覺得統一叫「加入單字庫」比較好懂，刪除確認也只要問「是否刪除…？」。
- **砍掉 CSV 匯出**：我決定不做 CSV 匯出，移到「明確不做」。
- **AI 例句不存**：我問 AI 解釋產生的例句要不要存。AI 建議不存，因為單字庫已經保存原句，那是實際讀到這個字的地方；再多一組例句加翻譯，表格會太擠，要看的話回原文再點一次就會從快取出現。
- **MCP**：加入 `search_vocab`、`add_to_vocab`、`delete_vocab`，以及配合一詞多義新增的 `delete_vocab_example`。工具和網頁共用同一個資料庫。AI 把「讀音空白時由原形推算」從 API 移進 `vocab_repo.add_vocab`，讓 API 和 MCP 都只是薄包裝；也用 MCP client 經 stdio 實際呼叫工具確認。
